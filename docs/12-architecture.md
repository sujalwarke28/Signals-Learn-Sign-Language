# 12 · Architecture

Written for someone reading the codebase for the first time — a reviewer, or you
in three weeks.

## 12.1 Layout

```
lib/
  main.dart                  entry point; Firebase init, prefs + sound loaded, ProviderScope
  firebase_options.dart      generated by flutterfire (gitignored)

  core/
    constants.dart           pass threshold, video-complete fraction, categories, topics
    config/app_config.dart   Cloudinary cloud name + preset (gitignored)
    sound/sound_service.dart pooled one-shot audio with debounce
    theme/app_theme.dart     seed -> light + dark ColorScheme, text theme, component themes

  models/                    plain immutable data + fromDoc/toMap
    app_user.dart            uid, email, displayName, role
    lesson.dart
    question.dart
    lesson_progress.dart     the per-lesson state machine's stored form
    quiz_attempt.dart        one finished quiz run
    forum_post.dart          post + reply
    progress_summary.dart    DERIVED stats — the only file that computes numbers
    
  data/                      everything that talks to Firestore or HTTP
    firestore_refs.dart      every collection path, named once
    auth_repository.dart
    lesson_repository.dart
    progress_repository.dart the three writes that move lesson state
    forum_repository.dart
    cloudinary_service.dart  unsigned multipart upload
    seed_data.dart           demo lessons, questions, forum threads
    seed_service.dart        writes the above through the repositories

  providers/                 Riverpod wiring; no business logic
    app_providers.dart       Firebase instances, repositories, injected singletons
    auth_providers.dart
    lesson_providers.dart
    progress_providers.dart  progressSummaryProvider lives here
    forum_providers.dart
    settings_providers.dart  theme mode, sound toggle

  router/app_router.dart     go_router: auth redirect + StatefulShellRoute tabs
  screens/                   one folder per feature area
  widgets/                   shared UI: Pressable, ProgressRing, LessonCard, common.dart
tool/                        asset generators (sounds, Lottie)
```

The rule that keeps it navigable: **widgets never touch Firestore**. A screen
watches a provider; a provider calls a repository; a repository is the only thing
holding a `FirebaseFirestore`. `models/progress_summary.dart` is pure Dart with no
Firebase import at all, which is why it's directly unit-testable — see
`test/widget_test.dart`.

## 12.2 Firestore data model

```
users/{uid}
  email, displayName, role: "learner" | "admin", soundEnabled, createdAt

  progress/{lessonId}
    status: "notStarted" | "inProgress" | "completed"
    videoCompleted: bool          <- unlocks the quiz
    quizPassed: bool
    bestScorePercent, attemptCount, lastPositionSeconds
    startedAt, completedAt, updatedAt

  attempts/{attemptId}            <- append-only
    lessonId, lessonTitle, category
    score, total, percent, passed
    answers: { questionId: selectedIndex }
    createdAt

lessons/{lessonId}
  title, description, category, durationSeconds
  videoUrl, thumbnailUrl, order, difficulty, isPlaceholderVideo, createdAt

  questions/{questionId}
    prompt, options: [4 strings], correctIndex, imageUrl?, explanation, order

forum_posts/{postId}
  authorId, authorName, title, body, topic, replyCount, createdAt

  replies/{replyId}
    authorId, authorName, body, createdAt
```

Two shape decisions worth noting:

* **Questions are a subcollection of their lesson**, not a top-level collection
  with a `lessonId` field. That makes the security rule a one-liner
  (`match /lessons/{id}/questions/{qid}`) and makes deleting a lesson's quiz
  obvious.
* **Progress and attempts live under the user**, not in top-level collections.
  The rule becomes "this user only", with no query-level filtering to get wrong.

## 12.3 The lesson state machine

Three states, and only two facts decide which one you're in:

```
notStarted ──video starts──► inProgress ──video watched AND quiz passed──► completed
```

Both facts are stored as booleans on the progress document, and `status` is
re-derived from them on every write rather than being set directly. The whole
machine is one function in `progress_repository.dart`:

```dart
static LessonStatus _statusFor({required bool videoCompleted, required bool quizPassed}) {
  if (videoCompleted && quizPassed) return LessonStatus.completed;
  return LessonStatus.inProgress;
}
```

Three writes can move it, each in a transaction:

| Write | Trigger | Effect |
| --- | --- | --- |
| `markVideoStarted` | First frame of playback | → `inProgress` (won't demote a completed lesson on a rewatch) |
| `markVideoCompleted` | Position ≥ 95% of duration | `videoCompleted = true`; unlocks the quiz |
| `submitAttempt` | Quiz finished | Writes the attempt **and** folds the result into progress |

Passing threshold: **70%** (`AppConstants.passThresholdPercent`). Video counts as
watched at **95%** — trailing frames are unreachable on some codecs, so demanding
100% would leave quizzes permanently locked.

## 12.4 How live progress works

This is the part worth understanding, since "progress must be real and live" was a
hard requirement.

**Nothing derived is stored.** There is no `completionPercent` field anywhere in
Firestore. Instead:

```
lessonsProvider        (stream: lessons collection)        ─┐
progressMapProvider    (stream: users/{uid}/progress)      ─┼─► progressSummaryProvider
attemptsProvider       (stream: users/{uid}/attempts)      ─┘        (pure computation)
                                                                          │
                                        ┌─────────────────────────────────┤
                                   Dashboard                        Progress screen
                                   Results card                     Settings stats
```

`progressSummaryProvider` is a plain `Provider` that watches the three
`StreamProvider`s and calls `ProgressSummary.from(...)`. When any stream emits, it
re-runs. No caching, no invalidation to remember, no manual refresh anywhere in
the app.

The moment that makes it visible: `submitAttempt` writes the attempt document and
the progress document **in one transaction**. Both streams fire, the summary
recomputes, and every screen watching it rebuilds. That's why the results screen
can honestly say "Updated just now" and why the dashboard percentage has already
moved by the time you navigate back.

What gets computed (`models/progress_summary.dart`):

| Stat | Derivation |
| --- | --- |
| Completion % | progress docs with `status == completed` ÷ total lessons |
| Average score | mean of the **best** attempt per lesson, so retries help rather than dilute |
| Per-category | lessons grouped by category, each with completion and average |
| Day streak | consecutive days back from today with ≥1 attempt; alive if you practised today or yesterday |
| Perfect runs | attempts where `score == total` |
| Badges | pure functions of the stats above, so they light up live |
| Continue lesson | first `inProgress` lesson, else the first unfinished one |

The unit tests in `test/widget_test.dart` pin all of this down — best-attempt
averaging, streak gaps, category grouping, badge thresholds.

## 12.5 State management

Riverpod 3, classic API. A few conventions:

* `StreamProvider` for anything Firestore. `ref.keepAlive()` on the big ones
  (lessons, progress, attempts, forum posts) so tab switches don't re-fetch and
  flash a spinner.
* `Notifier` + `NotifierProvider` for small mutable UI state (filters, search,
  theme mode, sound toggle). `StateProvider` isn't in Riverpod 3's main API.
* `Provider` for derived values — `filteredLessonsProvider`,
  `progressSummaryProvider`, `categoriesProvider`. Cheap, synchronous, no
  `AsyncValue` juggling in widgets.
* `SharedPreferences` and `SoundService` are loaded in `main()` and injected via
  `overrideWithValue`, so everything downstream reads them synchronously.

## 12.6 Routing

`go_router` with a `StatefulShellRoute.indexedStack` for the four tabs, so each
tab keeps its own navigation stack and scroll position.

Full-screen flows — video player, quiz, results, new post, add lesson, settings —
are pushed on the **root** navigator, above the bottom bar. That's deliberate: a
learner mid-quiz shouldn't be able to tab away by accident.

The auth redirect holds on a splash screen until auth resolves (so a returning
user never sees a flash of the login screen), then routes signed-out users to
`/login` and bounces signed-in users off the auth screens. The router itself is
built **once** and re-evaluates its redirect via a `refreshListenable` — rebuilding
it on every auth change would tear down the navigation stack.

## 12.7 Video

`video_player` for playback, `chewie` for the controls. The player screen owns the
state machine's first half: it listens to the controller's ticks, marks the lesson
in progress on the first playing frame, and marks the video watched when position
crosses 95%. Scrub position is persisted every 5 seconds rather than every tick.

## 12.8 Uploads

Unsigned multipart POST straight to
`api.cloudinary.com/v1_1/{cloud}/video/upload` with the preset name. No API secret
is involved, because anything compiled into an APK or a web bundle can be
extracted from it — an unsigned preset is the only client-safe option. Cloudinary
probes the file and returns its real duration, so the admin never types it in, and
the poster frame comes free by swapping `/video/upload/` for `/image/upload/` and
asking for a `.jpg`.

## 12.9 Theming

One seed colour (`#6C5CE7`) through `ColorScheme.fromSeed()` for both brightnesses.
Everything else — surfaces, containers, on-colours — is Material 3's tonal output,
which is what keeps contrast sane and avoids the harsh combinations a hand-picked
palette drifts into.

Chosen on top of that: a `ThemeExtension` (`AppColors`) carrying streak amber,
success green and wrong red with separate light/dark values, plus one tint per
lesson category. Those carry meaning, so they shouldn't shift with the seed.

## 12.10 Deliberate simplifications

Worth being able to name, since they're the honest answer to "what would you do
differently at scale":

* **Sorting is client-side.** Lessons sort in Dart, the forum sorts in Dart. Avoids
  a composite index per list, and lets a document with an unresolved
  `serverTimestamp` appear immediately from its local snapshot instead of being
  dropped by a server-side `orderBy`. Fine at tens or hundreds of documents; a
  real library of thousands would need paginated server-side queries.
* **Quiz marking happens on the client.** Correct answers are readable by learners.
  That's right for a practice app — the explanation is shown immediately — and
  wrong for a graded exam, which would need a Cloud Function to mark, and therefore
  the Blaze plan.
* **Admin is a Firestore field, not a custom auth claim.** Costs one document read
  per admin write, and gains: the console can grant it with no Cloud Function.
* **`replyCount` is a denormalised counter**, incremented in the same batch as the
  reply so it can't drift.
* **Progress is recalculated client-side on every stream emission** rather than
  maintained by a Cloud Function. At this data volume it's a handful of list
  operations, and it means there is exactly one definition of each number instead
  of one in Dart and one in a function.
